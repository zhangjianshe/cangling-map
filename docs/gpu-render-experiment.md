# GPU 后台渲染实验

本分支用于验证 GPU 是否适合承担 Cangling Map 的矢量栅格化阶段，不改变生产渲染器。

## 基准边界

`gpu-render-bench` 使用同一批半透明矩形，对比：

- CPU：当前生产依赖 `tiny-skia` 的抗锯齿路径填充；
- GPU 冷路径：每次创建顶点 Buffer、目标纹理和回读 Buffer；
- GPU 常驻路径：复用显存中的顶点、目标纹理和回读 Buffer，只提交绘制并回读 RGBA。

这里有意包含 GPU 回读，因为 WMS/WMTS 最终仍需在 CPU 侧执行 PNG/JPEG 编码。基准不包含
GDAL 查询、投影、标签布局、字体塑形和图片编码，因此只是评估栅格化后端的上限，不能替代
真实中国行政区图层的端到端压测。

## 运行

```bash
cargo run --release -p gpu-render-bench
GPU_BENCH_ITERATIONS=30 cargo run --release -p gpu-render-bench
GPU_BENCH_ADAPTER=NVIDIA cargo run --release -p gpu-render-bench
```

输出为 CSV：图像尺寸、图元数量、CPU 耗时、GPU 总耗时和加速比。加速比大于 1 表示 GPU
更快。应分别记录集显、独显和无 GPU 容器的结果。

## 是否进入生产的判断条件

- 256×256 瓦片必须在包含上传和回读后仍有稳定收益；
- 并发压测的 P95 和吞吐量优于 CPU，而不是只有单请求平均值更好；
- GPU 故障时能自动降级到 CPU；
- 文字、halo、虚线、图案填充和抗锯齿输出与 CPU 后端可接受地一致；
- 容器能够稳定访问 `/dev/dri` 或 NVIDIA runtime。

如果小瓦片没有收益，更现实的落点是使用 GPU 处理大幅 WMS 合成、批量瓦片或预热任务，
而继续用 CPU 渲染普通 256/512 像素 WMTS 请求。

## 2026-10-21 首轮结果

测试设备为 Intel Raptor Lake-S UHD Graphics，后端为 Vulkan，release 模式，每组预热一次后
执行 10 次。GPU 总耗时包含顶点上传、离屏绘制、等待和 RGBA 回读。

| 尺寸 | 图元数 | tiny-skia CPU | GPU 总耗时 | 加速比 |
| --- | ---: | ---: | ---: | ---: |
| 256×256 | 250 | 0.828 ms | 7.695 ms | 0.11× |
| 1024×1024 | 2,000 | 51.174 ms | 11.790 ms | 4.34× |
| 2048×2048 | 8,000 | 743.492 ms | 80.659 ms | 9.22× |

结论：普通 256×256 单瓦片不适合逐请求提交 GPU；大幅 WMS 或合并批处理有明显潜力。下一轮
应使用真实行政区多边形，拆分 GDAL 查询、几何整理、GPU draw、readback 和 PNG 编码，并进行
多请求吞吐量与 P95 对比。

主机能够枚举 RTX 4060 PCI 设备，但当前 NVIDIA NVML 报告驱动/库版本不匹配，Vulkan 侧也
没有向 `wgpu` 暴露 NVIDIA adapter，因此本轮独显测试未执行。修复宿主机驱动后可使用
`GPU_BENCH_ADAPTER=NVIDIA` 重跑。

## 2026-10-21 RTX 4060 复测

重启主机后，NVIDIA 内核模块与用户态库统一为 `595.99.02`，`wgpu` 通过 Vulkan 正常选择
NVIDIA GeForce RTX 4060 Laptop GPU。release 模式、每组 10 次的结果如下：

| 尺寸 | 图元数 | tiny-skia CPU | RTX 4060 总耗时 | 加速比 |
| --- | ---: | ---: | ---: | ---: |
| 256×256 | 250 | 0.858 ms | 1.104 ms | 0.78× |
| 1024×1024 | 2,000 | 52.028 ms | 2.479 ms | 20.98× |
| 2048×2048 | 8,000 | 744.972 ms | 16.320 ms | 45.65× |

RTX 4060 大幅降低了固定提交与回读成本，但 256×256 单瓦片仍略慢于 CPU。结论保持不变：
普通小瓦片应继续走 CPU 或合并成批次提交；大幅 WMS、批量瓦片和缓存预热是 GPU 后端的
优先应用场景。

## 2026-10-21 显存常驻与 metatile 测试

顶点 Buffer、bind group、目标纹理和回读 Buffer 在测量前创建并驻留 GPU。每组执行 30 次，
下面用两轮结果的范围表示运行波动：

| 尺寸 | 图元数 | tiny-skia CPU | GPU 冷路径 | GPU 常驻路径 | 常驻加速比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 256×256 | 250 | 1.043–1.323 ms | 0.169–0.247 ms | 0.072–0.126 ms | 8.29–18.40× |
| 1024×1024 | 2,000 | 50.068–53.211 ms | 1.785–1.807 ms | 1.587–1.791 ms | 27.95–33.53× |
| 2048×2048 | 8,000 | 719.598–719.983 ms | 12.389–12.430 ms | 10.456–10.906 ms | 65.98–68.86× |

4×4 metatile 使用 1024×1024、4,000 个图元，常驻路径总耗时为 1.649–1.796 ms，摊到
一个 256×256 瓦片约 0.103–0.112 ms。该耗时已经包含 GPU 等待和整幅 RGBA 回读，尚未
包含切片和 PNG 编码。

这说明常驻显存能够解决小瓦片的固定资源创建与上传开销，metatile 又能进一步摊薄提交和
同步成本。不过当前场景仍是合成矩形，没有包含真实行政区多边形三角化、空间分块筛选、
属性规则、虚线、图案填充、字体塑形和标签碰撞，因此下一阶段必须用真实图层验证结果。

## 2026-10-21 真实中国行政区数据

测试直接读取现有 GeoServer 数据目录中的省、县和乡镇 Shapefile，使用 GDAL 空间过滤，
通过 Earcut 将 Polygon/MultiPolygon（包含内环）三角化，随后将去索引化三角形常驻显存。
GPU 时间包含绘制、等待和 RGBA 回读；预处理和首次上传单独列出，不计入常驻绘制。

| 数据与视口 | 输出 | 要素 | 三角形 | GPU 块 | 预处理 | 首次上传 | CPU | GPU 常驻 | 加速比 | 显存估算 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 全国省界 | 2048×1536 | 34 | 838,626 | 1 | 326.8 ms | 13.7 ms | 24.8 ms | 2.81 ms | 8.84× | 100.8 MB |
| 河南县界 | 1024×1024 | 491 | 524,592 | 1 | 133.2 ms | 6.4 ms | 36.5 ms | 1.11 ms | 32.93× | 56.0 MB |
| 河南乡镇 | 1024×1024 | 6,826 | 1,782,929 | 2 | 327.6 ms | 52.9 ms | 130.3 ms | 11.98 ms | 10.88× | 171.2 MB |
| 河南县界瓦片 | 256×256 | 35 | 62,099 | 1 | 34.0 ms | 1.3 ms | 3.19 ms | 0.375 ms | 8.50× | 6.2 MB |
| 河南乡镇瓦片 | 256×256 | 417 | 102,792 | 1 | 16.6 ms | 1.8 ms | 7.67 ms | 0.525 ms | 14.63× | 9.9 MB |

乡镇范围首次尝试生成了约 163 MB 的单一 storage buffer，超过设备 128 MB 的单 binding
上限。基准随后改为按设备限制自动拆成多个三角形块，并在同一个 render pass 中多次 draw；
河南乡镇范围最终拆成两个 GPU 块。这验证了生产实现必须采用空间分块，而不能按完整图层创建
单一 Buffer。

真实 256×256 视口依然得到 8.5–14.6× 的面填充加速，说明数据常驻后小瓦片也具备收益。
不过显存估算偏高，因为当前为了验证正确性使用去索引化顶点。生产版本应使用共享 vertex +
index buffer、按缩放级别简化、空间块裁剪和 LRU，预计可显著降低显存与 draw 工作量。

这些结果仍不包含边界线、虚线、图片填充、标签布局、glyph atlas 和 PNG 编码。它们必须在
正式 GPU 后端原型中分别计时，尤其要确认文字和编码不会成为新的主要瓶颈。

## 2026-10-21 索引网格、抗锯齿与边界线

生产原型已经抽取为独立的 `map-gpu` crate。面顶点不再按三角形重复，而是上传共享顶点和
`u32` 索引；目标使用 4× MSAA，再 resolve 到单采样 RGBA 纹理。边界线在预处理阶段展开成
1 像素四边形，乡镇边界支持按路径累计距离生成 6/4 像素虚线。以下为 RTX 4060、真实数据、
包含 RGBA 回读的常驻结果（3 次迭代）：

| 数据与视口 | 边界 | CPU | GPU | 加速比 | 显存估算 | MAE | 差异像素 >16 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 全国省界 2048×1536 | 1px 实线 | 101.1 ms | 4.0 ms | 25.6× | 229.0 MB | 0.45 | 0.68% |
| 河南县界 1024×1024 | 1px 实线 | 86.1 ms | 1.85 ms | 46.7× | 122.2 MB | 1.39 | 0.96% |
| 河南乡镇 1024×1024 | 1px 6/4 虚线 | 275.1 ms | 3.35 ms | 82.1× | 267.2 MB | 2.41 | 6.56% |
| 河南县界瓦片 256×256 | 1px 实线 | 8.28 ms | 0.32 ms | 26.0× | 13.1 MB | 1.44 | 1.35% |
| 河南乡镇瓦片 256×256 | 1px 6/4 虚线 | 16.2 ms | 0.57 ms | 28.7× | 15.6 MB | 2.30 | 5.64% |

实线场景的显著差异已低于 1.4%。虚线的差异像素较多来自 `tiny-skia` 与四边形展开在 dash
端点处不同的覆盖率，肉眼对比的虚线位置、长度和相位一致，平均通道误差仍低于 2.5/255。
基准支持 `GPU_BENCH_ASSERT_CORRECTNESS=1`：实线要求 MAE ≤3.5 且显著差异 ≤4%，虚线因
端点抗锯齿差异允许 ≤7%。该阈值用于回归拦截，不代表文字、图案填充已经通过生产验收。

当前线展开为每个线段 4 个顶点，在大范围乡镇视口上仍占用较多显存。接入服务前应改为
线段实例 buffer，或按空间块和缩放级别只保留请求需要的边界，从而避免整省细节常驻。

## 2026-10-21 中文文字与 halo atlas

文字继续复用生产 CPU 路径中的 Rustybuzz 塑形、TTF outline、粗体和 halo 绘制，只在字体、
字号、文字和颜色组合首次出现时生成可缓存的 RGBA patch。`map-gpu` 新增通用 atlas overlay，
将 patch 打包进纹理后使用带 UV 的索引四边形绘制。这样保持现有中文字体和标签布局语义，
也避免在 shader 中重新实现字体塑形。

RTX 4060 上将 12 个中文行政区名称（22px 粗体、2px 白色 halo）打包为 512×128 atlas，绘制
到 1024×512 目标并完成 RGBA 回读平均耗时 0.702 ms。输出已检查，无乱码、裁剪或 halo 丢失。
该数据只是 atlas 绘制基线；下一步仍需把真实图层的碰撞筛选结果转成 atlas 四边形，并比较
完整 WMS/WMTS 输出。

随后从 `xian201912.shp` 的真实河南范围复用生产投影缓存、空间查询、面积阈值、重复距离和碰撞
排序，导出 108 个已接受标签。GPU atlas 合成 1024×1024 并回读为 1.094 ms；与生产 CPU
透明标签层逐像素比较，MAE 1.018/255、显著差异像素 1.840%。标签位置、边缘裁剪、粗体和
halo 的视觉对比一致。布局本身首次执行约 382.6 ms，主要由投影数据查询、几何标签点计算、
字体塑形和碰撞构成；生产缓存键必须包含数据指纹、样式 revision、CRS、范围/空间块及缩放带。

RGBA overlay 已扩展为多纹理批次：标签 atlas 使用 clamp，独立图案纹理使用 repeat，因而可在
同一 render pass 中先绘制一个或多个 polygon fill-image，再绘制文字。16×16 双线性重复图案
裁剪到凹多边形，与生产 `tiny-skia::Pattern` 参考图比较，MAE 为 0.045/255，显著差异像素为
0.104%。图案与 12 个中文标签同时绘制到 1024×512 并回读约 0.66–0.70 ms。

## 2026-10-21 真实 WMS 驻留视口

服务端将场景资源与输出目标分离：网格和 atlas 按显存 LRU 保存，离屏纹理、4× MSAA 纹理及
回读缓冲按尺寸池化。WMS 首次请求默认准备 1.5 倍范围的驻留视口，后续同分辨率平移通过
uniform 视图变换直接绘制；带 64px 标签缓冲的省界、市界同样按实际扩展范围参与命中判断。
WMTS 保持精确瓦片范围，避免冷瓦片因过扫描增加准备成本。图层组成员改为并行渲染并直接
返回 RGBA，合成阶段不再执行成员 PNG 编码、解码和额外像素缓冲复制。

RTX 4060、debug 构建、`ai:china` 图层组、1969×1228 RGBA WMS 的一次受控结果：

| 路径 | 耗时 | 说明 |
| --- | ---: | --- |
| GPU 冷请求 | 7.52 s | 准备 1.5 倍省界、市界和南海线驻留视口 |
| GPU 驻留范围内平移 | 1.51 s | 三个成员场景全部命中 |
| GPU 相同视口热请求 | 1.49 s | 复用场景和输出目标 |
| CPU 相同视口 | 5.25 s | 相同图层组与输出尺寸 |

该大图热路径约为 CPU 的 3.5 倍，且平移请求不再退化到冷路径。冷请求因为额外准备 1.5 倍
范围而更慢，应通过预热、合理的显存预算和真实访问轨迹下的命中率换取交互阶段收益。当前热
路径的主要剩余成本是 GPU 回读、RGBA 图层合成和最终 PNG 编码。

## 2026-10-21 GPU 就绪网格持久缓存

GPU 场景准备结果新增版本化 `.cgmesh` 磁盘缓存，持久保存顶点、索引、图案纹理和标签 atlas。
服务进程重启后无需再次执行 GDAL 查询、投影、三角化、线展开和标签布局，只读取文件并创建
GPU buffer/texture。缓存使用数据及 Shapefile 伴随文件指纹、目标 CRS、生效样式、范围和尺寸
作为键，临时文件写完并同步后再原子替换。

RTX 4060、debug 构建、`ai:china`、1969×1228、2× 像素比的同一 WMS 请求结果：

| 路径 | 耗时 | 磁盘网格指标 |
| --- | ---: | --- |
| 首次构建 | 7.97 s | 0 命中、2 未命中、2 写入 |
| 重启后的首个请求 | 1.52 s | 2 命中、0 未命中、0 写入 |
| 人工截断一个缓存后 | 1.54 s | 1 命中、1 未命中、1 重建、1 错误 |

首次构建与重启后输出的 PNG 大小均为 394,860 字节，SHA-256 都是
`8167252035bddcc77afd031dbb0426f9e064249c79f035fe0980da71a6d13b62`。跨进程首屏耗时降低约
80.9%，损坏条目会自动删除并重建，未改变输出像素。
